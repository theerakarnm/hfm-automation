# AGENTS.md

Guidance for AI coding agents working in this repository.
Structure follows the open [AGENTS.md](https://agents.md/) format: plain Markdown, no special syntax.

## Project Overview

HFM-Automation is a Bun monorepo that pulls client and trading data from the HFAffiliates API and delivers it through LINE bot notifications, an internal Excel export site, and a report web app.

- Runtime: **Bun** - never use npm, yarn, or node commands.
- Language: TypeScript, ESM, strict mode.
- Core stack: Hono (web), Drizzle ORM + PostgreSQL 16, croner (scheduled jobs), pino (logging).

## Commands

Run from `apps/api` unless noted.

```bash
bun install                      # install deps (run inside each app)
bun run dev                      # dev server with watch
bun run start                    # production-style server
bun test                         # full test suite
bun test tests/webhook.test.ts   # one test file
bun test -t "wallet"             # tests whose name matches
bun run typecheck                # tsc --noEmit
```

Frontend (`apps/web-report-mock`): `bun run dev`, `bun run build`, `bun run lint`.

## Test Database

Repository tests run against a real PostgreSQL instance, not mocks.
Start it from the repo root:

```bash
docker compose up -d postgres-test   # localhost:5433, user test, db hfm_test
```

Set `TEST_DATABASE_URL=postgresql://test:test@localhost:5433/hfm_test`.
Tests drop and recreate tables (see `tests/db-helpers.ts`), so never point them at a real database.

## Architecture Rules (apps/api)

- Layering: `routes/` are thin HTTP handlers, `services/` hold business logic and external API calls (HFM, LINE), `repositories/` own all SQL through Drizzle.
- Routes never query the database directly; they call services or repositories.
- Cron jobs live in `src/jobs/` and are registered in `src/jobs/index.ts`; schedules are ICT (UTC+7).
- The LINE reply path must stay under the 60s reply-token expiry, so never let a reply await an unbounded HFM call (see `LAST_TRADE_DEADLINE_MS`).
- Keep the "why" comments. Comments here explain timing budgets and upstream API quirks that the code alone does not show.

## Multi-tenant

- Each LINE OA is one row in the `tenants` table; per-tenant settings are edited through the `/internal/config` UI and cached in memory for 60 seconds (invalidated on save).
- The public webhook URL shape is `https://host/webhook?oa=<webhook_id>`; the path form `POST /webhook/<webhook_id>` resolves the same way.
- Tenant resolution order: a missing or unknown `oa` id returns 404, a known but inactive tenant returns 200 without processing, the LINE signature is then verified with that tenant's own channel secret, and finally `destination` is cross-checked against the stored bot user id.
- On boot `initDb` seeds the first tenant from the eight legacy per-OA env vars exactly once, only when the `tenants` table is empty; no other code reads those vars.

## Environment & Security

- Copy `apps/api/.env.example` to `.env`; never commit `.env` or any real secret value.
- System secrets come from env only: `INTERNAL_API_KEY`, `CONFIG_ENCRYPTION_KEY`, `DATABASE_URL`, `TEST_DATABASE_URL`.
- Per-OA credentials (`LINE_CHANNEL_ACCESS_TOKEN`, `LINE_CHANNEL_SECRET`, `HFM_API_KEY`, plus the wallet, whitelist, and notify settings) now live in the database, encrypted at rest with `CONFIG_ENCRYPTION_KEY`.
- `CONFIG_ENCRYPTION_KEY` is base64 that decodes to exactly 32 bytes; a missing or invalid key kills the process at boot.
- `/internal/config` pages are protected by an httpOnly cookie session issued at `/internal/login` with `INTERNAL_API_KEY`, and mutating forms carry a CSRF token.
- `/internal/health`, `/internal/logs`, and `/internal/line-uids` keep the `?key=INTERNAL_API_KEY` mechanism (a valid cookie session also works) because the docker healthcheck uses it.
- The public webhook is protected by LINE signature validation and UID whitelist.

## Git Workflow

- Conventional commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.
- Subject line under ~50 characters, imperative mood, no agent co-author lines.
- Branches: `fix/<topic>` or `feat/<topic>`, merged into `main`.
- Run `bun test` and `bun run typecheck` before committing.

## Boundaries

- Never hand-edit migration SQL in `apps/api/drizzle/`; it is generated by `bunx drizzle-kit generate` from `src/db/schema.ts`.
- Never put real credentials into `.env.example`; it stays a template.
- Treat `apps/web-report-mock` as a throwaway mock, not the production frontend.
- Put plans and verification write-ups in `docs/plans/` with a dated filename.
